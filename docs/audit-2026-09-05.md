# Audit du 5 septembre 2026

Revue complète de WorkPulse : présence des fonctionnalités attendues, tenue
visuelle, justesse fonctionnelle, sécurité et charge.

Version auditée : `v0.4.0` — commit `e13276d`.

**Le produit est complet et fonctionnel.** Les trente-quatre exigences du
cahier des charges sont couvertes, la chaîne d'intégration est verte, et
l'application Android se compile et s'installe.

### Défauts corrigés

**Le bandeau d'alerte recouvrait le bouton de pointage.** L'alerte disait
« tu peux rentrer » et masquait « Pointer mon départ ». Le bandeau publie
désormais sa hauteur mesurée, et la page réserve la place correspondante.

**Le badge de l'anneau contredisait le message.** « −2h57 sur la journée »
s'affichait à côté de « tu peux partir ». Les deux étaient vrais ; juxtaposés
ils semblaient incohérents. Le badge dit maintenant « couvert par ton avance ».

**Les champs d'heure étaient tronqués** à « 08: » dans l'éditeur de journée :
la colonne était dimensionnée pour du texte, pas pour un champ de saisie.

### Points vérifiés et conformes

- Zones tactiles ≥ 44 px.
- Contraste du texte principal supérieur à 12:1.
- `prefers-reduced-motion` neutralise toutes les animations.
- Aucun débordement horizontal.
- Encoches et barres système respectées (`env(safe-area-inset-*)`).
- Rôles ARIA présents ; tous les champs ont un libellé.

## 4. Audit de sécurité

23 scénarios d'intrusion contre une vraie application et une vraie base. Détail
dans [docs/securite.md](securite.md).

### Le défaut critique

**Un compte pouvait écraser les pointages d'un autre.**

L'identifiant d'un pointage est produit par le client — c'est ce qui rend la
synchronisation idempotente. Mais il était déclaré unique pour **toute la
base**. Un `upsert` sur `where: { id }` atteignait donc la ligne de n'importe
quel compte.

Concrètement : Bob envoie une ligne portant l'identifiant d'une ligne d'Alice.
La ligne d'Alice est modifiée, et réattribuée à Bob.

La clé primaire est devenue le couple `(userId, id)`.

Le scénario existait dans le fichier de tests **avant** le correctif, avec le
commentaire décrivant le comportement attendu. Il décrivait ce qui aurait dû se
passer, pas ce qui se passait — c'est précisément à cela que sert un test
d'intrusion.

### Les autres vecteurs

| Vecteur | Résultat |
| --- | --- |
| Injection SQL dans une date | refusée par la validation de format |
| Injection SQL dans une note | stockée telle quelle, jamais exécutée |
| Opérateur déguisé en valeur | refusé |
| Traversée de chemin | refusée |
| Pollution de prototype | clés dangereuses écartées, prototype global intact |
| Jeton en paramètre d'URL | refusé |
| Jeton révoqué | refusé |
| Schéma d'autorisation détourné | refusé |
| Lot de 5 001 lignes | refusé |
| Corps de plus de 2 Mo | refusé avant désérialisation |
| Champ inconnu | refusé, jamais ignoré |
| Trace de pile dans une erreur | absente |
| En-têtes de sécurité | présents |

## 5. Audit de charge

### Le moteur, sur cinq ans d'historique

5 220 pointages, 260 semaines de report à remonter.

| Mesure | Budget | Observé |
| --- | ---: | ---: |
| État du jour | < 60 ms | ~16 ms au premier calcul |
| Report depuis le début du suivi | < 60 ms | < 1 ms une fois mémoïsé |
| Résumé d'une semaine | < 5 ms | < 1 ms |
| Un an de statistiques | < 40 ms | ~15 ms |

Le banc a révélé deux problèmes, tous deux corrigés :

**Un départ oublié continuait de courir.** Le code comptait tout segment ouvert
jusqu'à l'instant présent : un oubli du lundi valait cinquante heures le
mercredi. Ces minutes ne sont plus inventées ; la journée est signalée comme
incomplète.

**Le report était recalculé à chaque battement d'horloge**, soit toutes les
quinze secondes. Il est désormais mémoïsé sur l'identité des données. Six tests
prouvent que la mémoire s'invalide — un cache rapide et faux serait pire que
pas de cache.

### L'API, sur un compte d'un an

Quatre injecteurs : lecture complète, lecture incrémentale, calcul de solde,
écriture. Seuils sur les erreurs, les délais dépassés et la latence p99.

Exécuté par la chaîne à chaque poussée et chaque lundi.

## Méthode

L'audit n'a pas consisté à relire du code. Il a consisté à :

1. **écrire l'attaque avant la défense** — les tests d'intrusion ont été écrits
   en décrivant le comportement attendu, puis exécutés ;
2. **charger le moteur au-delà de l'usage réel** — cinq ans d'historique, là où
   un compte réel en compte un ou deux ;
3. **regarder les écrans** plutôt que les composants — trois défauts n'étaient
   visibles qu'à l'image ;
4. **exiger 100 % de couverture** sur le domaine, ce qui force à examiner chaque
   branche et à supprimer celles qui ne peuvent pas s'exécuter.

Les quatre approches ont chacune trouvé quelque chose qu'aucune autre n'aurait
trouvé.
